# --- PyTorch <-> JAX bridges (eval harness + torchax oracle path) --------
#
# Pin torch: torchax and torch_xla both track it exactly, and an unpinned
# torch silently installs a version torchax cannot import.
#
# Why 2.9 and not something newer: torch_xla's newest release is 2.9.0
# (Nov 2025) and it must equal the torch minor version, so torch_xla is what
# caps the whole chain. torchax 0.0.13 is the newest release and imports
# cleanly against torch 2.9 -- the failure recorded here previously (its
# autocast table referencing `aten.prod.dim_Dimname` and `aten.cholesky`,
# both removed in torch 2.14) does not occur on 2.9, where both ops still
# exist. Verified on this v6e-8 VM: `torchax.extract_jax` on a Linear+GELU
# module matches eager torch to 1.0e-3 (TPU default bf16 matmul precision;
# see the tolerance note in tools/torchax_oracle.py).
#
# CPU-only build: the default PyPI torch 2.9.0 wheel is CUDA-tagged and pulls
# ~3.5 GB of unused nvidia-*-cu12 deps onto a TPU VM. The `+cpu` local version
# only exists on the PyTorch CPU index (added via --extra-index-url at the top
# of this file, so every other package still resolves from PyPI). Neither
# torchax nor torch_xla declares a torch dependency, so nothing pulls the CUDA
# build back in.
torch==2.9.0+cpu
torchax==0.0.13

# torchax 0.0.13 imports flax but does not declare it -- without this,
# `import torchax` dies with ModuleNotFoundError: No module named 'flax'.
# Pinned to 0.12.8 because flax >= 0.12.9 requires jax >= 0.11.2 and would
# silently drag jax off the 0.11.0 pin above.
flax==0.12.8

# torch_xla provides `make_kernel_from_pallas`, which is what lets a Pallas
# kernel be called from a torch nn.Module on a TPU. evaluation/ is the only
# consumer; no tool in tools/ or server/ imports it.
#
# INSTALLED WITHOUT THE `[tpu]` EXTRA, AND IT CANNOT EXECUTE ON TPU HERE.
# torch_xla[tpu]==2.9.0 pins libtpu==0.0.21 and torch_xla[pallas] pins
# jax==0.7.1; either extra would tear down the jax 0.11.0 / libtpu 0.0.47
# stack this repo is built on. Bare torch_xla declares no libtpu at all, so
# it coexists -- but at runtime it then loads libtpu 0.0.47, whose PJRT C
# API is a year newer than torch_xla 2.9.0's framework side:
#
#   RuntimeError: Unexpected PJRT_ExecuteOptions size: expected 112, got 80.
#
# So `import torch_xla` and `make_kernel_from_pallas` work, and the CPU PJRT
# backend (PJRT_DEVICE=CPU) runs, but TPU execution raises the above. There
# is no fix by version choice today: torch_xla has shipped nothing since
# 2.9.0 (Nov 2025), and libtpu 0.0.47 is far newer. Revisit when a
# torch_xla built against libtpu 0.0.47+ ships; until then evaluation/ needs
# its own venv with the matching libtpu.
