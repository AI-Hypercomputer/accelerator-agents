# pallas_forge/tune/runner — warmup-disciplined kernel benchmarking

<!-- connect:up:begin -->
> **Cross-repo concept:** part of [pallas-kernel](../../../concepts/pallas-kernel.md) across this wiki's repos.
<!-- connect:up:end -->
[`BenchmarkRunner`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult) is the timing engine every `pallas-forge` measurement goes through, whether it's benchmarking one candidate Pallas kernel configuration or an XLA baseline for comparison — its whole reason to exist (per the module docstring) is getting the boring parts of TPU/GPU benchmarking right: separate warmup from timed iterations, force actual device completion with `jax.block_until_ready`, and report a full distribution (median/mean/std/min/max) rather than a single number.

## Entry points
- [`BenchmarkRunner.run_single`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.run_single) — benchmarks exactly one configuration; called both by [`BenchmarkRunner.run_all`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.run_all) (once per config in a sweep) and directly by each benchmark script's `xla_baseline` function (e.g. [`xla_baseline`](../catalog/benchmarks/bench_matmul.md#xla_baseline), [`xla_baseline`](../catalog/benchmarks/bench_rmsnorm.md#xla_baseline), [`xla_baseline`](../catalog/benchmarks/bench_swiglu.md#xla_baseline)) to get a single-config comparison timing for the unfused/XLA-native version of the same computation.
- [`BenchmarkRunner.run_all`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.run_all) — the sweep entry point; called from [`tune`](../catalog/pallas_forge/tune/__init__.md#tune) with the full list of configs a search strategy generated.

## Mechanism (step-by-step)
1. [`BenchmarkRunner.run_single`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.run_single) first calls [`input_fn`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.input_fn)`(config)` to materialize inputs for this specific configuration (coercing a non-tuple return into a one-element tuple), then runs [`n_warmup`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.n_warmup) untimed iterations of [`kernel_fn`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.kernel_fn)`(*inputs, **config)` each followed by `jax.block_until_ready` — this is what forces JIT compilation and cache-filling to happen *before* any timed measurement, so the timed loop measures steady-state execution, not one-time compile cost.
2. It then runs [`n_repeat`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.n_repeat) timed iterations, wrapping each call in `time.perf_counter()`...`jax.block_until_ready(out)`...`time.perf_counter()` — the `block_until_ready` call is what makes the measured interval reflect actual device execution rather than JAX's asynchronous dispatch returning immediately.
3. The collected millisecond timings are reduced to summary statistics (median, mean, std, min, max) via `numpy`, and optionally converted to throughput: if [`flops_fn`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.flops_fn) was supplied, `tflops = (total_flops / 1e12) / (median_ms / 1000.0)`; if [`bytes_fn`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.bytes_fn) was supplied, `bandwidth_gb_s` is computed the same way — both throughput metrics are derived from the *median* time specifically, not the mean, making them more robust to occasional slow outlier iterations.
4. The result is packaged into a [`BenchmarkResult`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult) — carrying [`config`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.config), [`median_ms`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.median_ms), [`mean_ms`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.mean_ms), [`std_ms`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.std_ms), [`min_ms`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.min_ms), [`max_ms`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.max_ms), the full [`all_times_ms`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.all_times_ms) list, and the optional [`tflops`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.tflops)/[`bandwidth_gb_s`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.bandwidth_gb_s) — a single object that is both the sweep's per-config record and the format `xla_baseline` functions return for one-off comparisons.
5. [`BenchmarkRunner.run_all`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.run_all) iterates every config, calling [`run_single`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.run_single) inside a `try/except` — a config whose kernel call raises (e.g. an invalid block-size combination that slipped past a `TuneConfig` constraint, or an actual TPU compilation failure) is skipped with a printed failure message rather than aborting the whole sweep, then the surviving results are sorted by [`median_ms`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.median_ms) ascending (fastest first) before returning.
6. [`BenchmarkResult.to_dict`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.to_dict) flattens a result for JSON/CSV export — every config key gets a `config_` prefix (to avoid collisions with the timing-field names) and the optional `tflops`/`bandwidth_gb_s` fields are included only if actually computed; this flattened form is what the report object (constructed via [`TuneReport.__init__`](../catalog/pallas_forge/tune/report.md#TuneReport.__init__)) uses for its export and heatmap methods, since a heatmap can be asked to plot `metric="tflops"` or `"bandwidth_gb_s"` even though those live as top-level `BenchmarkResult` attributes only when the corresponding `flops_fn`/`bytes_fn` was passed.

## Key data structures
- [`BenchmarkResult`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult) — the record type for one configuration's measurement; note it stores the *entire* [`all_times_ms`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.all_times_ms) list, not just the summary statistics, so a caller can recompute percentiles or inspect variance beyond std/min/max if needed.
- [`BenchmarkRunner`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.run_single)'s constructor fields — [`kernel_fn`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.kernel_fn), [`input_fn`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.input_fn), [`n_warmup`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.n_warmup) (default 5), [`n_repeat`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.n_repeat) (default 20), [`flops_fn`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.flops_fn), [`bytes_fn`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.bytes_fn) — a `BenchmarkRunner` instance is fully determined by these; it holds no state between `run_single` calls beyond the constructor's fixed configuration.

## Dynamics (design intent)
> [!inferred] The module docstring's stated goals — warmup passes, `jax.block_until_ready` for real execution time, statistical timing over repetitions — directly encode the three most common mistakes in ad-hoc TPU/GPU benchmarking (measuring compile time, measuring dispatch-not-execution time, and trusting a single noisy sample) as structural properties of this class rather than something each caller has to remember to do correctly.

## Edge cases
- [`BenchmarkRunner.run_all`](../catalog/pallas_forge/tune/runner.md#BenchmarkRunner.run_all) swallows *any* `Exception` from a failing config (bare `except Exception as e`), which means a systematic bug in `kernel_fn` that happens to raise on every config would silently produce an empty results list rather than a hard failure — the caller has to notice zero results, not receive a raised error.
- [`BenchmarkResult.to_dict`](../catalog/pallas_forge/tune/runner.md#BenchmarkResult.to_dict) only includes `tflops`/`bandwidth_gb_s` keys when they are not `None` — exporting a mix of results where some configs had `flops_fn` and others didn't would produce heterogeneous row shapes (handled downstream by [`TuneReport.to_csv`](../catalog/pallas_forge/tune/report.md#TuneReport.to_csv)'s union-of-keys fieldname logic, per that file's own docstring).
