# internal/xprof_client — OSS XProf HTTP + on-disk client
`OSSXprofClient` is the single client every xprof-mcp tool goes through to reach a running `xprof` profiler server — it wraps the server's HTTP plugin API (list runs/tools/hosts, fetch tool data) and, when the profiler's logdir is known, also reads the raw `.xplane.pb`/`.hlo_proto.pb` files directly off disk (or GCS) for tools that need the unprocessed trace rather than a pre-rendered view.

## Entry points
- [`get_runs`](../catalog/internal/xprof_client.md#OSSXprofClient.get_runs), [`get_run_tools`](../catalog/internal/xprof_client.md#OSSXprofClient.get_run_tools), [`get_hosts`](../catalog/internal/xprof_client.md#OSSXprofClient.get_hosts), [`get_hlo_module_list`](../catalog/internal/xprof_client.md#OSSXprofClient.get_hlo_module_list) — the discovery calls an MCP tool makes before fetching actual data: what runs exist, what tools/hosts a given run supports, and what HLO modules were captured.
- [`fetch`](../catalog/internal/xprof_client.md#OSSXprofClient.fetch) — the general-purpose data-fetch call every higher-level xprof-mcp tool (overview page, HLO stats, memory profile, graph viewer, etc.) ultimately routes through; it is a thin, tool-agnostic wrapper over the server's `/data/plugin/profile/data` endpoint.
- [`read_xplane_bytes`](../catalog/internal/xprof_client.md#OSSXprofClient.read_xplane_bytes) — the entry point for tools that need the raw XSpace protobuf directly from disk rather than a server-rendered view; requires the logdir to be known.

## Mechanism (step-by-step)
1. `OSSXprofClient.__init__` (visible in source, its own signature not directly in this packet's cited subgraph beyond the fields it assigns) sets [`_base_url`](../catalog/internal/xprof_client.md#OSSXprofClient._base_url) from an explicit argument, the `XPROF_URL` environment variable, or [`_DEFAULT_XPROF_URL`](../catalog/internal/xprof_client.md#_DEFAULT_XPROF_URL) (`"http://localhost:8791"`), in that priority order, and creates one [`_session`](../catalog/internal/xprof_client.md#OSSXprofClient._session) (`requests.Session`) reused across every subsequent HTTP call.
2. [`_logdir`](../catalog/internal/xprof_client.md#OSSXprofClient._logdir) is resolved similarly (explicit argument, then `XPROF_LOGDIR` env var), but falls back to [`_detect_logdir_from_procfs`](../catalog/internal/xprof_client.md#_detect_logdir_from_procfs) if still unset — this only works when the xprof server is reachable at `localhost`/`127.0.0.1`/`::1`, since it works by inspecting `/proc` on the *local* machine, not the server's.
3. [`_detect_logdir_from_procfs`](../catalog/internal/xprof_client.md#_detect_logdir_from_procfs) is a three-step chain entirely over Linux's `/proc` filesystem: (a) scan `/proc/net/tcp`/`/proc/net/tcp6` for a listening (`state == "0A"`) socket bound to the target port, recovering its inode; (b) scan every PID's `/proc/<pid>/fd/*` symlinks for one pointing at `socket:[<inode>]`, recovering the owning process; (c) read that process's `/proc/<pid>/cmdline` and parse out the `--logdir=`/`--logdir`/`-l` argument. Any failure at any step (`OSError`, missing permissions, non-Linux, or the broad `except Exception` at the top level) returns `""` silently rather than raising — this is best-effort auto-detection, not a required capability.
4. Every listing/fetch method — [`get_runs`](../catalog/internal/xprof_client.md#OSSXprofClient.get_runs), [`get_run_tools`](../catalog/internal/xprof_client.md#OSSXprofClient.get_run_tools), [`get_hosts`](../catalog/internal/xprof_client.md#OSSXprofClient.get_hosts), [`get_hlo_module_list`](../catalog/internal/xprof_client.md#OSSXprofClient.get_hlo_module_list), [`fetch`](../catalog/internal/xprof_client.md#OSSXprofClient.fetch) — follows the same shape: build a `params` dict, call `self._session.get(f"{self._base_url}/data/plugin/profile/<endpoint>", params=..., timeout=...)`, then `resp.raise_for_status()` before extracting the payload (`.json()` for structured endpoints, `.text.strip()` for the module list, `.content` for `fetch`'s raw bytes) — this uniform pattern means an HTTP error from the xprof server always surfaces as a `requests.HTTPError`, not a swallowed empty result.
5. [`fetch`](../catalog/internal/xprof_client.md#OSSXprofClient.fetch) accepts arbitrary `**kwargs` merged into the query params (documented example: `type='long_txt'` for the graph viewer tool) — this is what lets `fetch` stay tool-agnostic: it doesn't need to know every tool's specific parameter set, just forward whatever the caller supplies alongside the mandatory `run`/`tag` (tool name).
6. For direct-disk access, [`get_session_dir`](../catalog/internal/xprof_client.md#OSSXprofClient.get_session_dir) calls [`_require_logdir`](../catalog/internal/xprof_client.md#OSSXprofClient._require_logdir) (which raises `RuntimeError` with a corrective message if `_logdir` is still empty after both the env-var and procfs-detection attempts) and joins `<logdir>/plugins/profile/<run>` — the fixed directory layout xprof's TensorBoard-plugin-style server itself uses. [`get_xplane_file_path`](../catalog/internal/xprof_client.md#OSSXprofClient.get_xplane_file_path) then appends `<host>.xplane.pb` to that session directory.
7. [`read_xplane_bytes`](../catalog/internal/xprof_client.md#OSSXprofClient.read_xplane_bytes) resolves the path via [`get_xplane_file_path`](../catalog/internal/xprof_client.md#OSSXprofClient.get_xplane_file_path), checks existence with [`_gfile_exists`](../catalog/internal/xprof_client.md#_gfile_exists), and — if missing — lists the session directory via [`_gfile_listdir`](../catalog/internal/xprof_client.md#_gfile_listdir) to include the *actually available* files in the raised `FileNotFoundError` message, before finally reading bytes via [`_gfile_read`](../catalog/internal/xprof_client.md#_gfile_read) on the success path.

## Key data structures
- `OSSXprofClient` — holds [`_base_url`](../catalog/internal/xprof_client.md#OSSXprofClient._base_url), [`_logdir`](../catalog/internal/xprof_client.md#OSSXprofClient._logdir), and [`_session`](../catalog/internal/xprof_client.md#OSSXprofClient._session); exposed read-only via the [`base_url`](../catalog/internal/xprof_client.md#OSSXprofClient.base_url) and [`logdir`](../catalog/internal/xprof_client.md#OSSXprofClient.logdir) properties.
- The `_gfile_*` helpers ([`_gfile_exists`](../catalog/internal/xprof_client.md#_gfile_exists), [`_gfile_listdir`](../catalog/internal/xprof_client.md#_gfile_listdir), [`_gfile_read`](../catalog/internal/xprof_client.md#_gfile_read)) — each branches on [`_is_gcs`](../catalog/internal/xprof_client.md#_is_gcs) (a `path.startswith("gs://")` check) to either use `tf.io.gfile` (lazily imported, so `tensorflow` stays an optional dependency) or plain `os`/`open` calls — this is the abstraction that lets every disk-reading method in the client work unmodified whether the logdir is a local path or a GCS URI.

## Dynamics (design intent)
> [!inferred] The module's own docstring frames `XPROF_LOGDIR` as "required for tools that read raw .xplane.pb/.hlo_proto.pb files directly from disk... Optional when the xprof server runs on localhost — the logdir is auto-detected from the server process cmdline via /proc." This states the tradeoff directly: the HTTP-fetch methods ([`fetch`](../catalog/internal/xprof_client.md#OSSXprofClient.fetch) and friends) never need the logdir at all (they only need `_base_url`), while the disk-reading methods ([`read_xplane_bytes`](../catalog/internal/xprof_client.md#OSSXprofClient.read_xplane_bytes) and the `get_*_file_path` helpers) need it unconditionally, with procfs auto-detection existing purely to spare a user running the server locally from having to set the env var manually.

## Edge cases
- [`_detect_logdir_from_procfs`](../catalog/internal/xprof_client.md#_detect_logdir_from_procfs) explicitly bails (`return ""`) for any hostname other than `localhost`/`127.0.0.1`/`::1` — a remote xprof server always requires `XPROF_LOGDIR` to be set explicitly for disk-reading tools to work; there is no remote equivalent of the procfs trick.
- [`get_hlo_module_list`](../catalog/internal/xprof_client.md#OSSXprofClient.get_hlo_module_list) returns a plain comma-separated string (`resp.text.strip()`), unlike every other listing method here which returns parsed JSON (`resp.json()`) — callers must split it themselves.
- The global singleton (`get_client()`/`set_client()`, visible in source but outside this packet's cited subgraph) means the client's environment-derived configuration (`_base_url`, `_logdir`) is captured once at first use; changing `XPROF_URL`/`XPROF_LOGDIR` after the first `get_client()` call has no effect unless `set_client()` is called to replace the instance.
